# 開発ワークフロー

## 基本原則

- 要所だけ確認して自走する: 方針と、方針に関わる判断だけユーザーに確認し、それ以外は PR のレビュー取り込みと CI 成功まで自走する
- 早期フィードバック: 動く状態を早く作り、確認を得る
- 小さな積み重ね: 小さな単位で実装し、動作確認を繰り返す

## ブランチ戦略（GitHub Flow）

本プロジェクトでは GitHub Flow を採用する。

### ブランチの種類

- **デフォルトブランチ**（`main` / `master`）: 常にデプロイ可能な状態を維持する。直接コミットしない
- **作業ブランチ**: タスクごとにデフォルトブランチから作成する。命名規則:
  - 形式: `<type>/<kebab-case-description>`
  - 小文字の英数字とハイフンを使用
  - type の種類:
    - `feature/` — 新機能・改善・バグ修正（例: `feature/add-user-auth`）
    - `support/` — メンテナンス・ドキュメント・依存関係更新など（例: `support/update-dependencies`）

### フロー

```
デフォルトブランチ ─── feature ブランチ作成 ─── 実装・コミット ─── PR 作成 ─── レビュー ─── マージ ─── デフォルトブランチに戻る
```

1. **ブランチ作成**: `git fetch origin` の後、`git switch -c {ブランチ名} origin/{デフォルトブランチ}` で作成（前のタスクの未マージのコミットを持ち込まない）
2. **実装・コミット**: 小さな単位でコミットを積み重ねる
3. **PR 作成・レビュー**: `/autodev-start-task` が `/autodev-create-pr` で PR を作り、`/autodev-review-pr` でレビューし、指摘を取り込んで CI の成功まで確かめる
4. **マージ・切り替え**: ユーザーが `/autodev-merge-and-switch` を呼び、マージ条件を確かめてマージし、デフォルトブランチに戻る

### レビュー形式

プロジェクトのレビュー形式に応じて、以下のいずれかのフローを使用する（`autodev-init` で選択）。

#### GitHub レビュー

GitHub の Review 機能を使ってレビューする。

1. `/autodev-review-pr` で reviewer サブエージェントが GitHub にレビューコメントを投稿する（レビューのみ）
2. `/autodev-start-task` が指摘を取り込んで修正・push し、行コメントのスレッドに対応結果を返信して解決する

#### ローカルレビュー

ローカルの diff を使って Claude がレビューし、結果をファイルに保存する。

1. `/autodev-review-pr` で reviewer サブエージェントがローカルの diff をレビューし、`.ai-agent/tmp/reviews/` に結果を保存する（レビューのみ）
2. `/autodev-start-task` が指摘を取り込んで修正・コミット・push し、レビューファイルに対応結果を追記する

人間のレビュアーが後から付けたコメント、`/autodev-review-pr` を単体で実行したときの指摘、セッションをまたいで取り込みを再開する場合は、専用のスキルを使わず、会話の中で個別に対応する（修正・push・コメントへの返信を依頼する）。

### 注意事項

- デフォルトブランチへの直接プッシュは避ける
- マージ方式はマージコミット（`merge commit`）を使用する
- マージ済みのフィーチャーブランチはリモートで自動削除されることを前提とする

## タスク実行フロー

`/autodev-start-task` が次を 1 本の流れで行う。

1. 仕分け（はっきりしない要件の確認、survey / project に回すか）と下調べ
2. 方針（目的・方針・完了条件・ブランチ名）をユーザーに確認し、タスクの README を作成
3. ブランチを作り、区切りごとに lint / テストで確かめながら実装・コミット
4. PR を作成（`/autodev-create-pr`）し、レビュー（`/autodev-review-pr`）
5. 指摘を取り込む。Critical / Warning は直し、Info は妥当なものを直す。方針に関わる指摘だけユーザーに確認する。Critical を直したらレビューをやり直す
6. 最後の push の CI が通るまで待つ（落ちたら直して再 push）
7. ブランチに未コミット・未 push の変更が無いことを確かめ、ユーザーに完了報告
